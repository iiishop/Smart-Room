# Device Association Pipeline — Cross-Modal Matching Spec

## Overview

Bridge VR visual identification with network-layer device discovery through a
multi-tier fallback matching system. The two sides share one common substrate:
the MQTT broker — all devices publish to it, all systems subscribe to it.

```
                    MQTT Broker (shared)
                         │
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
    Discover         VR System       Lab Devices
 (network side)    (visual side)    (publishers)
         │               │
         │   ┌───────────┘
         │   │
         ▼   ▼
    Device Profiles ←──→ VLM Descriptions
              │
              ▼
         Match Engine
              │
    ┌─────────┼─────────┐
    │         │         │
   Tier 1   Tier 2   Tier 3
   LLM     Identify  Manual
   match   protocol   select
```

## Architecture: Three Tiers

### Tier 1 — LLM-Based Semantic Matching (primary, zero-config)

**Discover side**: Every 60 seconds, a profiling agent collects all events for
each device and calls an LLM to generate a dynamic device profile.

**VR side**: When the user gazes at a device, VLM analyzes the image and produces
a visual description. The same (or a coordinating) LLM compares this description
against all current device profiles and selects the best match.

If the device is a known commercial product (e.g. Govee H5179), VLM may output
the exact model name directly. The matching step then becomes a simple string
lookup against device profiles that mention that model.

### Tier 2 — Operation-Based Identification (fallback, no firmware change)

Two strategies, tried in order:

**2a. Existing Capability Trigger (preferred)**

Use already-discovered device operations (from the operation pipeline). If
a device is known to have a switch/toggle/control topic, publish a test
command and watch for visual change:

```
VR publishes:  govee/.../switch ← {"value": "on"}
Camera sees:   one device's LED lights up → device matched
```

No firmware changes needed — the operation pipeline has already
discovered the capability by observing topic patterns. The camera detects
state change (light on/off, screen toggle, relay click) and associates it
with the commanding device.

**2b. Dedicated Identify LED (backup)**

If no usable operation is discovered, fall back to a standard identify
topic. The device responds with a visible signal (LED flash, screen
indicator). The camera detects which device is responding.

Requires each device to implement a `device/identify` handler. For DIY
lab devices, this is a firmware-level change.

### Tier 3 — Manual Selection (last resort)

User points at a device in VR, sees the Discover device list sorted by recent
activity, and selects the matching entry. After selection, the spatial position
and device_id are bound — no further manual input needed for that device.

## Component Design

### 3.1 Device Profile (Discover side, new)

A machine-readable summary of what a device IS, what data it PRODUCES, and what
operations it SUPPORTS. Generated by LLM from raw event logs, updated every 60s.

```python
@dataclass
class DeviceProfile:
    device_id: str                    # "device-1"
    generated_at: float               # timestamp
    # Inferred identity
    device_type: str                  # "temperature/humidity sensor"
    possible_models: list[str]        # ["Govee H5179"] or []
    vendor_guess: str | None          # "Govee" or None
    # Capabilities
    data_outputs: list[str]           # ["temperature", "humidity"]
    supported_operations: list[str]   # [] or ["power_toggle", "set_temperature"]
    # Confidence
    confidence: float                 # 0.0 – 1.0
    # Raw evidence summary (for LLM prompt)
    evidence_summary: str             # condensed recent events
```

**Generation**: Every 60s, for each device, compile the last N events into a
structured prompt and call an LLM (e.g. GPT-4o-mini) to produce a JSON profile.

**Persistence**: Profiles are published to an MQTT topic
`discover/profiles/{device_id}` so the VR system can subscribe and receive
live updates without polling.

### 3.2 VLM Visual Description (VR side, new)

When the user gazes at a device, the VR headset captures a frame and sends it
to a VLM with a structured prompt:

```
You are analyzing a lab IoT device. Describe:
1. Physical appearance (shape, size, color, display type)
2. Any visible text, labels, or model numbers
3. Any visible indicators (LEDs, screens showing values)
4. Your best guess at what type of device this is
5. If you recognize the model, state it exactly

Output as JSON:
{"appearance": "...", "visible_text": "...", "indicators": "...",
 "device_type_guess": "...", "recognized_model": null}
```

### 3.3 Match Engine (shared, new)

Receives a VLM description, fetches current device profiles (from MQTT
`discover/profiles/#`), and calls an LLM to select the best match:

```
Below is a visual description of a device observed through a VR headset:

[VLM_DESCRIPTION]

Below are profiles of devices discovered on the network:

[DEVICE_PROFILES]

Which device profile best matches the visual description?
Consider: device type, capabilities, any model names, and physical hints.
If no profile is a reasonable match, say "NONE".

Output as JSON:
{"matched_device_id": "device-3", "confidence": 0.85, "reasoning": "..."}
```

**Confidence threshold**: ≥ 0.7 → accept match. < 0.7 → fall to Tier 2.

### 3.4 Identification Protocol (both sides, new)

**Strategy A — Capability Trigger (no firmware change needed):**

When the operation pipeline has discovered a usable capability (e.g. a
`switch` topic), the VR system publishes a test command to that topic:

```
govee/.../switch ← {"value": "on"}     # use discovered operation topic
```

The camera detects a visual state change (LED lights up, screen toggles,
relay clicks) and associates the change with the commanding device. This
requires NO firmware change — it uses already-observed operation patterns.

**Strategy B — Dedicated Identify (firmware fallback):**

If no usable operation is discovered, fall back to a standard identify
topic:

```
device/identify/{device_id}    ← VR publishes {"action": "identify", "duration_s": 3}
device/identify/ack/{device_id} ← Device publishes {"status": "identifying"}
```

**Device handler** (firmware-side, per-device, only if no operation available):

```
on_message("device/identify/{my_device_id}"):
    if msg.action == "identify":
        flash_led(msg.duration_s)
        publish("device/identify/ack/{my_device_id}", {"status": "identifying"})
```

**VR detection**: The VR system monitors the camera feed for a visual change
(LED blink, screen text change, state toggle). If detected, the device is
bound.

### 3.5 Manual Binding (VR side, fallback)

VR UI: user points at a device → system shows the Discover device list (sorted
by `last_seen` descending) → user taps the matching entry → `(spatial_position,
device_id)` saved to persistent store.

## Data Flow

```
Time ──────────────────────────────────────────────────────────→

Every 60s:
  Discover ──→ compile events ──→ LLM profile generation
                                  ──→ publish to discover/profiles/{id}

On user gaze:
  VR ──→ capture frame ──→ VLM description
       ──→ fetch discover/profiles/# (latest)
       ──→ LLM match engine
              │
              ├─ confidence ≥ 0.7 → bind device ✓
              ├─ confidence < 0.7 → Tier 2 identify
              │                       │
              │                       ├─ detected → bind device ✓
              │                       └─ timeout → Tier 3 manual ✓
              └─ no match → Tier 2
```

## Open Questions

1. **LLM cost/latency**: 60s profiling on N devices × per-gaze matching. Cost
   acceptable? If not, profile less frequently (5 min) and cache.

2. **VLM quality on lab devices**: DIY devices with no labels, no screens, just
   a breadboard — VLM may output "electronic circuit board" which is useless for
   matching. In that case, Tier 1 fails fast → Tier 2 identify takes over.

3. **Identify protocol reliability**: Requires every device firmware to handle
   `device/identify`. What about devices the lab doesn't control the firmware of?
   → They skip Tier 2, fall directly to Tier 3 manual.

4. **Profile sharing mechanism**: MQTT `discover/profiles/#` is simple but adds
   broker traffic. Alternative: REST endpoint on Discover, VR polls. MQTT is
   simpler for real-time updates.

## Success Criteria

- Tier 1 correctly matches a Govee H5179 (commercial device with recognizable
  topic patterns) against its visual appearance within 3s of gaze
- Tier 2a correctly associates a device with a known switch topic by triggering
  it and detecting the visual state change within 3s of command
- Tier 2b correctly associates a DIY breadboard sensor using LED identify within
  5s of command
- Tier 3 manual binding completes within 10s of user interaction
- Profiles update within 60s of new device data appearing
