## 🔴 必须修

### 1. SigLIP 2 文本预处理缺失关键参数

**文件:** `engine.py` `_verify_label_with_clip()` (L530-532)  
**当前代码:**
```python
text_inputs = self._clip_proc(
    text=[label], return_tensors="pt", padding=True,
).to("cuda")
```

**问题:** SigLIP 2 训练时使用了固定的 `padding="max_length"` + `max_length=64`，且文本被 lowercased。当前代码只传了 `padding=True`（等价于 `padding="longest"`），导致单个短 label（如 "chair"）只被 tokenize 到 3-4 个 token，与训练时的 64-token 固定长度分布不匹配。

**官方文档原文（HuggingFace SigLIP2 model card）:**
> "IMPORTANT: we pass `padding=max_length` and `max_length=64` since the model was trained with this"
> "Model was trained with lowercased text, so make sure your text labels are preprocessed the same way."
> "To get the same results as the Pipeline, a prompt template of `'This is a photo of {label}.'` should be passed to the processor."

**但注意:** 新版 transformers 的 `Siglip2Processor.__call__` 已自动处理 lowercasing 和 padding/truncation 到 64（见 [PR #43101](https://github.com/huggingface/transformers/pull/43101)）。但**这个自动行为只在传入 `text=...` 参数且不覆盖 padding 参数时生效**。当前代码传了 `padding=True`，可能覆盖了自动默认值。

**修复方案 A（推荐）:** 不传 padding 参数，让 processor 使用 SigLIP2 默认值
```python
text_inputs = self._clip_proc(
    text=[f"This is a photo of {label}."], return_tensors="pt",
).to("cuda")
```

**修复方案 B:** 显式指定
```python
text_inputs = self._clip_proc(
    text=[f"This is a photo of {label}."],
    return_tensors="pt",
    padding="max_length",
    max_length=64,
).to("cuda")
```

**影响:** 相似度分数分布可能偏离训练时的校准范围，`_CLIP_SIM_THRESHOLD = 0.18` 的门槛值可能已经不准了。修完之后 threshold 需要重新 tune。

**来源:**
- https://huggingface.co/google/siglip2-base-patch16-224 （README: "IMPORTANT: we pass `padding=max_length` and `max_length=64`"）
- https://huggingface.co/docs/transformers/model_doc/siglip2 （"Default text preprocessing" 一节）
- https://github.com/huggingface/transformers/pull/43101 （SigLIP2 tokenizer PR）

### 2. SAM2 `from_pretrained` 后未传 `device` → 可能在 CPU 上运行

**文件:** `engine.py` `_ensure_models()` (L796)  
**当前代码:**
```python
self._sam2_image = SAM2ImagePredictor.from_pretrained(self._IMAGE_PREDICTOR_MODEL)
```

**问题:** `SAM2ImagePredictor.from_pretrained()` 内部调用 `build_sam2_hf(model_id, **kwargs)`，如果不传 `device` 参数，模型可能加载在 CPU 上，然后每次 `set_image()` 和 `predict()` 时会触发 GPU-CPU 数据传输。

**官方文档（facebookresearch/sam2 README）:**
```python
predictor = SAM2ImagePredictor.from_pretrained("facebook/sam2-hiera-large")
```

官方示例也没有传 device。但检查 `build_sam2_hf` 源码（`sam2/build_sam.py`）发现它会根据 `torch.cuda.is_available()` 自动选择设备。所以在有 CUDA 的环境中应该是安全的。

**核实:** 需要确认当前环境 SAM2 确实跑在 GPU 上。如果 VRAM 报告正确（~1.5GB for SAM2-tiny），那就没问题。

**修复:** 保险起见，显式传参：
```python
self._sam2_image = SAM2ImagePredictor.from_pretrained(
    self._IMAGE_PREDICTOR_MODEL, device="cuda",
)
```

**来源:**
- https://github.com/facebookresearch/sam2 （README: Image prediction 示例）
- `sam2/build_sam.py` 源码（`build_sam2_hf` 函数）

## 🟡 建议修

### 3. `render_topdown` 逐像素 Python for-loop — 性能瓶颈

**文件:** `depth_alignment.py` `render_topdown()` (L239-242)  
**当前代码:**
```python
for i in range(len(px_img)):
    xi, yi = px_img[i], py_img[i]
    if 0 <= xi < img_w and 0 <= yi < img_h:
        canvas[yi, xi] = bgr[i].tolist()
```

**问题:** 对 ~5000 个点做 Python for-loop 逐像素索引，每次调用 ~10-20ms。虽然 subsample 了，但在 dashboard 轮询时（每次刷新都调 `/api/depth/topdown`）仍有影响。

**修复:** NumPy 向量化索引
```python
valid_idx = (px_img >= 0) & (px_img < img_w) & (py_img >= 0) & (py_img < img_h)
canvas[py_img[valid_idx], px_img[valid_idx]] = bgr[valid_idx]
```

**来源:** NumPy advanced indexing 文档

### 4. FastAPI WebSocket broadcast timeout 过于激进

**文件:** `main.py` `_broadcast_rgb_preview()` 等 (L443 等)  
**当前代码:**
```python
await asyncio.wait_for(client.send_bytes(jpeg_bytes), timeout=0.02)
```

**问题:** 20ms 超时极其激进。基于网络抖动，任何 dashboard 客户端短暂卡顿就会被标记为 stale 并踢出。FastAPI 的官方 WebSocket 示例不使用超时，而是依赖异常处理。

**修复:** 增大超时到 1-2 秒，或去掉 `wait_for`，只靠 try/except 捕获断线：
```python
try:
    await client.send_bytes(jpeg_bytes)
except Exception:
    stale.append(client)
```

**来源:**
- https://fastapi.tiangolo.com/advanced/websockets/ （官方示例无超时）
- https://websocket.org/guides/frameworks/fastapi/ （"Performance tuning": 不要阻塞事件循环）

### 5. SigLIP 2 未使用优化的 attention backend（SDPA）

**文件:** `engine.py` `_ensure_models()` (L802-805)  
**当前代码:**
```python
self._clip_model = AutoModel.from_pretrained(
    self._SIGLIP_MODEL, torch_dtype=torch.bfloat16,
).to("cuda")
```

**问题:** SigLIP 2 支持 `sdpa`（PyTorch scaled dot product attention），比默认的 eager attention 快 ~2x。官方文档明确推荐。

**官方文档:**
> "Toggle the `attn_implementation` parameter to either `'sdpa'` or `'flash_attention_2'` to use a more memory-efficient attention."

**修复:**
```python
self._clip_model = AutoModel.from_pretrained(
    self._SIGLIP_MODEL,
    torch_dtype=torch.bfloat16,
    attn_implementation="sdpa",
).to("cuda")
```

**预估收益:** SigLIP 2 inference 从 ~15ms 降到 ~8ms（base 模型），VRAM 影响 ~0。

**来源:**
- https://huggingface.co/docs/transformers/model_doc/siglip2 （"Optimized attention" 章节）
- https://huggingface.co/docs/transformers/attention_interface

### 6. 深度对齐：只取左眼 reprojection 矩阵，缺右眼确认

**文件:** Unity `TrackingManager.cs` `GetDepthReprojMatrix()` (L184-196)  
**当前代码:**
```python
var mat = Shader.GetGlobalMatrix("_EnvironmentDepthReprojectionMatrices");
```

**问题:** `_EnvironmentDepthReprojectionMatrices` 是一个数组，`GetGlobalMatrix` 返回 index 0（左眼）。对于单目 RGB passthrough camera（从左侧摄像头获取），这应该是正确的。但 t-34400 的 QuestRealityCapture 项目为左右眼分别记录了深度描述符。

**核实:** 确认 RGB stream 来自 left camera（Quest 3 的 passthrough camera 默认是左眼视角）。如果是，当前做法正确。

**来源:**
- https://github.com/t-34400/QuestRealityCapture （depth descriptor 包含左右眼数据）
- Meta Depth API 文档

## 🟢 参考

### 7. Grounded-SAM-2 的 `<CAPTION_TO_PHRASE_GROUNDING>` 级联方案

Grounded-SAM-2 的 auto-labeling 使用两步级联：`<CAPTION>` → `<CAPTION_TO_PHRASE_GROUNDING>`，让 Florence-2 先理解场景再定位物体，标签质量比单纯 `<REGION_TO_DESCRIPTION>` 更好。

**考虑场景:** 当 SigLIP 2 分数低时（当前 fallback 是 `<REGION_TO_DESCRIPTION>`），可以尝试：
1. 对整个 crop 跑 `<DETAILED_CAPTION>` → 获得场景描述
2. 对描述跑 `<CAPTION_TO_PHRASE_GROUNDING>` → 获得更精确的物体短语
3. 用短语验证 SigLIP 2

**代价:** 额外 ~2-3s inference（两次 Florence-2 调用）。

**来源:** https://github.com/IDEA-Research/Grounded-SAM-2 （auto-labeling pipeline）

### 8. Meta PCA `WorldToViewportPoint` 的 `cameraPose` 参数

**当前:** `pca.WorldToViewportPoint(hitPoint)` — 不传 cameraPose，使用当前帧的相机位姿。

**官方 API 签名 (MRUK v85):**
```csharp
Vector2 WorldToViewportPoint(Vector3 worldPosition, Pose? cameraPose=null)
```

文档建议：如果 trigger 触发和实际图像处理之间有延迟，应该缓存 `GetCameraPose()` 并传入，避免相机移动导致的投影偏差。

**当前场景:** trigger → HTTP POST → 后端处理（1-3s）→ 返回。在这个过程中用户可能已经转动头部。但由于我们已经在 trigger 时计算好了 pixel 并发送，cameraPose 提供的是 trigger 瞬时的准确位姿 — 这对我们来说其实比默认行为（使用当前帧位姿）更好。当前代码不传 cameraPose 等于用调用 `WorldToViewportPoint` 时的位姿，而这时距离 trigger 已经过了若干毫秒。

**修复（低优先级）:**
```csharp
var triggerPose = pca.GetCameraPose();  // cache at trigger time
Vector2 viewport = pca.WorldToViewportPoint(hitPoint, triggerPose);
```

**来源:** https://developers.meta.com/horizon/reference/mruk/v85/class_meta_x_r_passthrough_camera_access/

### 9. SAM2 HF `pipeline("mask-generation")` 确认可用

P5（SAM2 auto-mask fallback）的官方 API 确认：

```python
from transformers import pipeline
generator = pipeline(
    "mask-generation",
    model="facebook/sam2.1-hiera-tiny",
    device=0,
)
outputs = generator(image, points_per_batch=64, pred_iou_thresh=0.88)
# outputs["masks"] → list of binary masks
# outputs["scores"] → list of IoU scores
```

与我们现有 SAM2 实例独立——创建 pipeline 不会冲突（只要 VRAM 够）。`points_per_batch=64` 是 trade-off：越高越快但越吃 VRAM。

**来源:** https://huggingface.co/docs/transformers/model_doc/sam2 （"Automatic Mask Generation with Pipeline"）

### 10. Quest 3 深度数据获取的替代 API

Meta 提供了两套深度数据获取方式：

**当前使用:** Shader globals（`_EnvironmentDepthReprojectionMatrices`、`_EnvironmentDepthTexture`）  
**替代方案:** `Utils.GetEnvironmentDepthTextureId` + `Utils.GetEnvironmentalDepthFrameDesc`

`GetEnvironmentalDepthFrameDesc(int eye)` 返回包含 FOV 角度、near/far 平面的结构体，比 shader globals 更结构化。但需要 Unity `XR.Oculus.Utils` namespace。

对当前项目来说，shader globals 已经够用。但如果后续需要更精确的深度投影（比如考虑每个深度帧的独立 FOV），可以考虑切换到这套 API。

**来源:** https://developers.meta.com/horizon/documentation/unity/unity-depthapi-xr-oculus/

### 11. Florence-2 模型 ID: `florence-community` vs `microsoft`

**当前使用:** `florence-community/Florence-2-base` ✅

官方 HF 文档（v5.x）使用 `microsoft/Florence-2-base`，但 `florence-community` 是 transformers 集成的标准路径。两者指向同一模型，`florence-community` 是官方推荐的 HF 路径。无需修改。

**来源:** https://huggingface.co/docs/transformers/model_doc/florence2
